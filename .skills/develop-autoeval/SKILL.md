# AutoEval 开发与 PR 流程

## 接续已有任务

1. 先运行 `git status --short --branch`、`git remote -v` 和 `git worktree list`。接续任务时从用户指定的分支、已有 PR 或上次交接定位工作树。在候选目录核对 `git rev-parse --show-toplevel`、`git rev-parse HEAD` 和未提交改动。已有 PR 同时核对仓库、base 和 head；区分本地新增提交与已推送版本。
2. 独立需求从确认并已获取的目标分支创建 `feat/<主题>`，用户指定其他名称时沿用。当前目录有其他任务的修改时，用 `git worktree add -b feat/<主题> <新目录> origin/<目标分支>` 隔离工作。阅读选定版本的 AGENTS.md、README.md、相关实现与锁文件。
3. 把验收写成用户能观察的结果。跨层需求分别写页面与执行侧的判据，例如同一 SSH 主机显示四个数据集节点，并按数据集查到各自的容器 ID。样本数、预算或环境有限时，注明限制来自产品规则、用户授权还是本次测试取样。修复缺陷先定位复现路径或能暴露差异的测试。

## 实现与验证

| 改动落点 | 实施和验证 |
| --- | --- |
| 页面、API 或共享类型 | 一起核对后端校验、OpenAPI、前端类型与调用点。在 frontend/ 运行 `npm run build`；版本有模块边界检查时运行 `npm run check:boundaries`。可见交互按 backend/tests/browser_checks/README.md 验证相应路径。 |
| 后端业务规则 | 在 backend/ 使用锁定的 Python 3.12 环境，运行 `uv run ruff check .` 和受影响的 pytest；改共享契约时扩大回归。保留单团队、单工作空间语义。 |
| 数据库结构变更 | 新增 Alembic revision，在隔离 PostgreSQL 从受支持的旧 revision 升到目标 head。合并分叉迁移时分别验证两个来源，回读受影响的历史记录及关联。 |
| 报告查询、榜单或图表 | 按改动选历史数据核对数值、引用、证据状态和页面。例如调整精度图横坐标时，用两个数据集分别核对准确率、对应基线和坐标标签。涉及计分时覆盖缺测、评分失败与合法零分。 |
| 调度、取消或重试 | 核对冻结输入、执行集合、Outbox 幂等、回执未知与重启恢复。记录每次尝试，核对未选样本的新增派发数。外部 I/O 放在 Temporal 活动或适配器中。真实执行、分析或探测依本次目标、资源及预算授权。 |
| 文档、Skill 或 CI | 文档核验链接、命令目录和入口。Skill 校验 frontmatter、相对引用及可执行示例；CI 变更以实际工作流运行结果为准。对本次改动运行 `git diff --check`，已暂存内容用 `git diff --cached --check`。 |

记录被测提交（含本地改动时注明）、环境、命令、结果和跳过条件。分别注明模拟响应、固定产物、真实基础设施、远程执行和模型调用的证据范围。密钥、受保护配置、备份和分享包留在受保护位置。启动方式、对外接口或验收边界有变化时，同步更新对应指南。

## 提交与 PR 标题

需要分段提交时，按可以独立验收的行为拆分，每段把实现与对应回归放在一起。例如资源调度可分别交付数据集节点分配、预检复用、按主机展示节点。小改动可用一个提交。每次提交前逐路径检查暂存差异，开 PR 前检查相对 base 的完整差异。用户要求分段推送时，随已验证的各段推送。

使用 `类型(范围): 中文动作与对象`。冒号和其后的一个空格使用半角字符。标题描述整个 PR 的主要变化；先看相对 base 的 diff，再参考提交和正文。沿用项目的产品名、数据集名和代码标识。

- **类型**按结果选择。新增能力用 `feat`，修正行为用 `fix`，仅改说明用 `docs`，等价重构用 `refactor`，流水线用 `ci`，仅测试用 `test`。多种改动服务于同一目标时，取能表达该目标的类型。
- **范围**选主要领域或组件，如 `evaluation`、`reporting`、`identity`、`frontend`、`skills`。优先沿用仓库内已使用的名称。摘要写明行为、适用对象，必要时写触发条件。分支名、孤立的需求编号和“完成功能开发”都不足以说明变化。
- **示例**：`fix(evaluation): 单 Case 重试按本轮受理时间计算执行期限`；`ci(github): 为 PR 添加后端测试和前端构建检查`。
- **正文**说明问题与用户可见结果，列出本次验证、失败或未覆盖范围。存在迁移、后台角色变更或回滚依赖时补充发布顺序和恢复条件。有需求或设计链接时附上。

批量规范已有 PR 时使用[历史 PR 标题维护流程](references/pr-titles.md)。

## 交付与交接

按当次授权推进提交、推送、开 PR、合并或部署。交付时说明实际到达的阶段。

- 用户要求**本地体验**时，先核对前端、API 和相关 Worker 的工作目录、启动配置或镜像。端口已有监听者时先识别所属任务。若多个分支的 Worker 同时轮询同一队列，使用隔离的预览环境验证执行链。用浏览器走通指定路径，给出访问地址、点击步骤和预期结果。
- 用户要求**合入 PR**时，核对 base、head 和最新 SHA，等待必需检查与评审，修复可处理的失败并复验。合并后回读 PR 状态和目标分支上的合并提交，给出 PR 链接与 SHA。
- 用户要求**部署验收**时，按[部署 Skill](../deploy-autoeval/SKILL.md) 核对目标环境实际运行的镜像、对应提交和数据库 revision，从用户入口验证受影响路径。按业务链路附可回查的 `run_id`、`report_id` 或 Trace ID。代码、镜像或配置变化后重验受影响的结论。

跨聊天接续时，在当前聊天末尾或已有 PR 的交接说明中留一行，只填本次有值的字段。

`工作树 / 分支 / HEAD ｜ 已验证的用户路径与环境 ｜ 访问地址或运行标识 ｜ PR / 部署状态 ｜ 下一步或阻塞`
