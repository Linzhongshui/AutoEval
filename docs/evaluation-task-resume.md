# R12 取消后续跑测评与单 Case 重试

**开发设计与验收记录。** 用户在原任务详情可以续跑已取消任务的剩余样本，也可以从 Case 列表选定一个样本重试。任务 ID、详情链接、模型、配置版本、工具身份和完整样本清单沿用首次提交的冻结快照。每次确认新增一个执行轮次。用户能查到每份结果来自哪次尝试，也能查到哪次取消停止了后续派发。

## 取消、证据保全与核对

1. **停止领取新作业。** 取消与领取分片在数据库中锁定同一任务并核对当前轮次。取消先提交时，新领取失败；派发意图先提交时，该分片进入原作业核对范围。执行端在发起样本请求前持久化作业、冻结样本与原生尝试的对应关系，收到终态后追加结果。请求已发出但回执丢失时，保留该次尝试和用量记录。
2. **在清理前保存现场。** 对已提交作业使用原提交键查询或取消，等待远端终态。收集已完成样本的预测、原生评分、请求记录和可用统一输出，按原样本身份核对，写入持久化对象存储并回读校验 SHA-256。脱敏后的归档引用记录作业、样本、尝试和来源文件。对象写入失败可重新采集；回读通过后清理失败可单独重试。保留尚待采集的远端文件。
3. **分别确认取消和释放。** 所有可能已提交的作业均须有终止依据，每个已取得的容量租约均须有清理确认和释放记录。对从未领取、从未生成派发意图的分片可直接确认未执行。进程退出、取消接口返回和数据库中的 `cancelled` 各自只证明对应事实。
4. **判定样本去向。** 以原快照和清单哈希为起点，按数据集、样本 ID、样本哈希及冻结的尝试规则核对历轮记录。一个样本只进入下表的一行。远端作业终止后仍需核对已发出的模型请求，监控完成数仅用于展示。

| 预览分类 | 判定依据 | 用户确认后的处理 |
| --- | --- | --- |
| 可复用 | 所需原生尝试齐全，执行和评分均有终态，关联证据可读且哈希一致。合法零分计入此类。 | 引用原尝试 ID 和证据哈希。仅缺评分但同次原生材料足够时，先恢复评分、校验后再归类。 |
| 待补跑 | 有可靠记录证明未派发、明确失败或中止，且没有结果未知的在途请求。 | 按冻结清单执行，列出样本 ID 与原因。 |
| 证据丢失需补跑 | 已查明原尝试结束，核对归档和可用原始产物后确认材料永久丢失或损坏。 | 单列样本及原因，计入用户明确确认的补跑总数，保留原尝试。 |
| 待核对 | 请求回执不明、远端失联、仅有进度计数、身份冲突，或对象存储暂时不可读。 | 阻塞整轮续跑。后台只查询原作业、请求与产物，证据变化后再计算预览。 |

## 轮次、执行清单与投递

**持久化边界。** 新增执行轮次记录，保存 `run_id`、轮次号、来源轮次、操作类型（首次执行、整任务续跑、单 Case 重试）、操作者、取消请求与确认时间、原快照哈希、确认清单及其摘要。单 Case 重试另存目标数据集与样本 ID。数据库分别约束同一任务的轮次号唯一、同一来源轮次最多一个后继。已有数据集子执行保留为逻辑数据集，在其下新增按轮次归属的执行分片。分片 ID 用作远端提交键和租约所有者，监控、日志与归档同时关联分片和轮次。首轮既有作业保留原提交键。

**精确选择。** 从快照的有序样本中取“待补跑”与“证据丢失需补跑”的并集。比如 GPQA 待补的原始索引为 1、2、5，则提交 `[1:3]` 和 `[5:6]` 两个左闭右开区间；MMMU-Pro 同理。DeepSWE 和 AutomationBench 则使用冻结的原生任务名筛选。派发前展开工具实际配置，验证各分片互斥、并集恰好等于确认清单，同时检查工具身份、尝试次数和总并发。若工具无法在冻结条件下精确选择，返回原因。配置副本用于本次派发，原快照始终供核验。

**受理与重试。** 服务端对确认请求先按幂等键及来源轮次查找既有受理记录，再检查当前状态。首次受理时锁定任务，复核操作类型、来源终态、作业终止与清理凭据、清单摘要及预算条件。整任务续跑还需确认取消记录。在同一事务内创建轮次、分片、事件和 Outbox，更新当前轮次与状态。需要执行时沿用原预算账户、余额和截止时间；预算过期或原资源、模型身份无法核验时返回阻塞原因。整任务续跑没有待补样本时直接进入汇总。

分发器以任务和轮次构造稳定的 Temporal Workflow ID，分片派发意图在外部 I/O 前落库。分发器崩溃可重投同一意图；远端提交回复不确定时按原提交键查询。每一次状态投影都核对当前轮次，迟到的旧回执归档到原轮。重新取消会产生新的来源轮次，旧确认请求始终指向原先创建的后继。

**样本历史。** 新的真实执行追加平台尝试号，同时保留工具原生尝试号。归档重试按分片、样本和原生尝试去重，相同身份出现不同内容时记录冲突并停止合并。复用只写来源引用。涉及多次原生尝试时，按冻结工具规则选取满足条件的完整尝试组，并记录哪些尝试参与计分。历轮实际请求和已发生用量累计可查。

## 接口与用户操作

以下为拟新增接口，共用前缀 `/api/autoeval/v1/evaluation-tasks/{id}`。

| 接口 | 输入与响应 |
| --- | --- |
| `GET /resume-preview` | 返回来源轮次、可否确认、阻塞原因、各数据集四类样本的数量与明细、待重新执行的总数及 `scope_sha256`。摘要绑定原快照、来源轮次、有序样本身份、分类与证据引用。读取预览不会创建执行。 |
| `POST /resume` | 必填 `Idempotency-Key`，请求体携带 `source_round` 和 `scope_sha256`。首次受理返回 HTTP 202、原 `run_id` 和新轮次。相同确认重放返回已受理轮次。键与内容冲突、预览过期或条件不满足返回 HTTP 409 及原因。 |
| `GET /case-retry-preview` | 查询参数为 `dataset_key`、`sample_id`。由服务端按冻结清单定位一个样本，返回样本哈希、最近尝试、原生成绩与证据状态、冻结的原生尝试数、来源轮次和确认摘要。摘要同时绑定操作类型与目标，跨操作、跨样本使用时失效。 |
| `POST /case-retry` | 必填 `Idempotency-Key`，请求体含 `dataset_key`、`sample_id`、`source_round`、`scope_sha256`。核验成功返回 HTTP 202、原任务 ID、新轮次及目标样本。清单中找不到该数据集与样本组合时返回 404；同键异参、来源已变化或执行条件不满足时返回 409。 |

两页以不同键确认同一来源轮次且范围相同，返回同一后继；相同来源但摘要不同，要求刷新预览。已经受理的轮次不可随证据变化扩大范围。派发前若发现足以改变确认集合的变化，停止尚未派发的工作并记录原因，重新核对。

用户从原任务详情打开“续跑测评”。确认页显示“将重新执行 N 个样本”，按数据集列出复用数和补跑数，并突出证据永久丢失的样本及原因。阻塞时展示对应作业、样本或资源，以及最近一次核对结论。原详情按轮次查看取消事件、分片、尝试、日志和报告；任务列表按原任务保留一行。进度分母取原清单样本数，分子分别展示已复用与本轮新增完成的去重样本数。

### 单 Case 重试

1. **选定样本。** 当前轮次终态为已取消、失败或已完成，原作业已终止、资源已释放时，用户可以从原任务详情对一个冻结样本发起重试。即使从历史尝试行进入，也按当前轮次预览目标样本。失败、中止、未派发和已成功样本均可选。样本存在结果未知的请求或证据暂时不可读时，先完成核对。能用同次材料恢复评分的先恢复并刷新预览。确认框列出数据集、样本 ID、原尝试与成绩，说明将重新执行 1 个 Case、追加尝试和用量；已有有效成绩时同时提示新报告将采用本轮结果。
2. **限定实际派发。** 建立只含该样本的分片。AISBench 原始索引为 `i` 时仅提交 `[i:i+1]`；Harbor 仅提交该样本的原生任务名，并沿用冻结的原生尝试次数。一个 Case 可对应多次原生尝试或多次模型请求。服务端必须验证工具展开后的样本集合恰好为所选样本，执行期间也只为该分片分配租约和归档键。即使同一数据集中另有失败或缺测 Case，其新增派发数仍为零。
3. **处理并发点击。** 单 Case 重试与整任务续跑共用任务锁、来源轮次唯一约束和 Outbox。同一来源、同一 Case、同一摘要重复确认，即使请求键不同，也返回原受理轮次。不同 Case 或整任务续跑争用同一来源时，只受理先提交的操作，另一方收到 409 和当前轮次。用户可在本轮终止、清理并重新预览后继续重试任一 Case，包括再次重试同一 Case。
4. **回看结果并继续。** 本轮报告只更新所选 Case 的结果引用，其余按来源版本逐项承接，包括原有缺测。用冻结规则对新尝试组评分，保留合法零分。重试失败或缺少评分时，新版本展示实际状态和空缺成绩；既有版本仍可查看原成绩。整份报告的分母始终取原清单。若来源任务因取消留下其他待补样本，本次结束后仍可从最新轮次续跑，沿用原取消记录并重新计算剩余集合；任务列表继续展示已取消及剩余数，轮次历史单独展示这次 Case 重试的结果。

## 报告、兼容与发布

结束一轮时，按原始样本顺序生成结果索引，每条指向参与计分的尝试及其证据，保留所属轮次。用整份索引按数据集原生规则计算成绩。缺测、执行失败、评分失败与证据当前不可用分别表达；缺失成绩保持空值，不计算基准差值。报告分别记录历史执行完整性 `validity` 和读取时的 `evidence_status`，多数据集各自展示成绩。

以新增 Alembic 迁移将报告约束从按任务唯一调整为按任务和版本唯一。任务持有一个当前报告指针，对象写入和回读校验完成后，才在事务中插入不可变版本并切换指针。重复汇总同一轮、同一索引时返回同一版本。取消时生成的部分报告、后续完整报告都保有独立 ID、对象和哈希。任务详情和报告列表读取当前版本；按报告 ID 查询、已有榜单记录和分析继续读取其绑定版本。同次执行的证据修订可作为具名来源，其用途见[任务报告与恢复归档](task-report-recovery.md)。

迁移将既有统一编排任务解释为首轮，将既有报告登记为首个当前版本，保留原快照、事件、尝试及对象引用。历史取消任务缺少派发或清理凭据时显示具体阻塞原因。上线依次部署迁移、兼容读写的 API 与后台进程、具备部分归档能力的执行端，最后开放续跑入口。回退时先关闭新续跑受理，已受理轮次由兼容版本完成或核对；保留新增数据及报告引用。

准备好目标环境后，在后端执行 `uv run alembic upgrade head`，部署 API、分发器与工作流及规划执行 worker。确认这些进程使用同一版本后，在 API 和执行 worker 配置 `AE_EVALUATION_FOLLOW_UP_ENABLED=true` 并重启进程。配置默认关闭，关闭时确认接口返回 503。API 详情返回入口可用性，前端据此显示操作。

## 验收用例

基础夹具固定同一模型、清单和评分规则，以受控执行器的实际请求记录核对样本集合和调用次数。各环境已覆盖的范围见下文。

| 编号 | 输入与操作 | 判定依据 |
| --- | --- | --- |
| R12-01 部分完成后取消 | 原清单 10 个样本，4 个已归档、1 个已发出、5 个未派发。保存取消意图，分别在远端终止前、租约释放前、在途样本查清前直接请求续跑。 | 取消后没有新领取的作业，三次请求均未创建后继轮次。已完成的 4 份证据在远端清理后仍可回读。 |
| R12-02 核对在途样本 | 对同一夹具分别提供成功且可校验的终态证据、明确中止的凭据，以及持续未知的回执。 | 前两种预览分别为复用 5、补跑 5 和复用 4、补跑 6。第三种继续阻塞。三种核对的新增模型调用数均为 0。 |
| R12-03 续跑完成 | 提交确认，捕获各分片实际执行 ID，读取新旧报告和原任务详情。 | 实际集合等于确认集合，复用样本新增调用数为 0。新报告覆盖全部 10 个样本，成绩与同一组固定原生结果整体计分一致。任务 ID 和快照哈希一致，原取消事件、尝试、用量及旧报告可回查。 |
| R12-04 重复与故障 | 模拟双击、不同键并发、同键不同内容、响应丢失、Outbox 重投、提交回执丢失。第二轮取消后重发第一轮确认。 | 同一来源只创建一个后继、一条启动意图；每个分片最多实际提交一次。冲突请求返回 409，旧确认返回第二轮，第三轮只能由新的明确确认创建。 |
| R12-05 边界与兼容 | 构造非连续 AISBench 缺口、Harbor 多尝试、多数据集和合法零分。分别模拟永久丢证、暂时不可读、预算过期、全部可复用及历史信息不足。 | 捕获实际区间、任务名和尝试次数核对清单。零分可复用，永久丢证单列确认，暂时不可读或去向不明时阻塞，有新增执行且预算过期时拒绝。全部复用时只生成汇总，模型调用数为 0。 |
| R12-06 只重试所选 Case | 在两个数据集中设置相同的样本 ID，并在目标数据集保留另一缺测样本。分别从失败行、未派发行发起重试，覆盖 AISBench 和 Harbor 多尝试配置。 | 捕获的分片只含指定数据集的指定样本，原生尝试数与冻结配置一致。其他样本新增请求数为 0。任务 ID 和分母稳定，只有目标追加尝试与用量。取消任务中其余待补样本仍可整任务续跑。 |
| R12-07 历史与报告 | 对已有有效成绩的 Case 重试，分别返回较低合法分数、零分和执行失败。 | 新报告分别引用本轮较低分、零分或失败，历史尝试和旧报告均可按原 ID 查得。其他 Case 的结果引用逐项一致，已发布榜单仍绑定原报告。 |
| R12-08 并发与受理边界 | 双标签确认同一 Case，再分别模拟不同 Case 和整任务续跑竞争、过期预览、未知回执、未释放租约及预算过期。 | 相同确认只产生一个轮次、一个分片和一条启动意图；竞争者收到 409。其余阻塞场景均无新增派发。可在结束后用最新预览再次重试，重放此前已受理的请求仍返回原轮次。 |

在隔离的 PostgreSQL 上验证迁移、唯一约束、并发与旧报告引用；以受控执行器及持久化对象存储验证部分归档、故障重试和实际派发；以浏览器验证原详情确认、刷新和历史回看。验证记录分别注明环境、夹具、实际结果与跳过项。真实远程测评和模型调用按另行授权的目标、范围及预算执行。

### 已验证范围

- 隔离 PostgreSQL 与本机持久化 S3 的四组受控集成测试通过，覆盖在途样本成功和中止、租约释放前拒绝续跑、提交回执丢失后按原作业核对、单 Case 派发、剩余样本续跑、证据损坏后重新确认及报告切换。执行器使用固定产物，模型调用数为零。DeepSWE 和 AutomationBench 的选择测试确认单 Case 分片只保留指定原生任务名，并沿用冻结的尝试次数与并发限制。
- 本机 Temporal 独立命名空间跑通了 HTTP 受理、Outbox 投递、worker 活动到报告写入的受控链路。两组浏览器拦截式测试通过，覆盖从原任务详情确认整任务续跑，选择待执行 Case 并确认重试，以及查看历史分片日志。
- 本机 Linux 容器按源码锁核验 AISBench 源码后，使用固定预测和原生参考答案离线调用 GPQA 与 MMMU-Pro 的原生评分器。两条路径均得到预期的零分和满分。另用容器中的文本和多模态推理类验证非零起始切片的派发记录先于模型传输写入。传输与缓存接收器使用本地替身，真实远端取消及收集联动仍待验收。
- 本机 Docker 验证了按已登记 Compose 项目清理测试网络、保留其他项目网络、拒绝 daemon 身份不一致及幂等回查。另在隔离控制容器运行锁定版 Harbor 0.21.0 与两个本地 Oracle trial。一项完成并产出原生评分，另一项在归属容器启动后中止。两项均写入 trial 派发记录，清理回查确认其 Compose 容器和网络已移除。该试验直接加载派发钩子和清理函数，未经统一任务 API、正式适配器或模型服务。
- Linux 执行容器用固定产物作业验证了远端运行时的真实提交、进程组取消、终态确认、部分结果保全、派发记录读取和重复清理。作业驱动为替身，模型调用数为零。
